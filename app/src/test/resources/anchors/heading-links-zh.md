## 1. 学术建模与 Markdown 公式规范

不要采用“公式堆叠式建模”，而应按照符合硕士论文写作习惯的递进式建模过程展开：

**提出问题 → 引入变量 → 建立模型 → 说明作用 → 引出下一模型。**

网页对话中的数学变量与公式使用 `\(...\)` / `\[...\]` 表示。

MD 文件内部：

- 所有正文中的变量统一采用 `$...$`；
- 独立公式统一采用 `$...$`；
- 短公式统一采用 `$...$`；
- 对于与 Markdown 渲染器不兼容的公式，应改写为 Markdown 兼容的 LaTeX 格式；
- 变量解释使用连续的一段文字，不采用逐条堆叠形式。

变量说明格式示例：

> 其中，变量表示意义；变量表示意义；变量表示意义。

生成内容时，应保持建模叙述的连续性与论文逻辑，避免只罗列公式而缺少变量引入、物理意义、约束来源及模型之间的衔接关系。

## 2. SVG 拆解与 PPT 生成规范

将 SVG 图片中的内容拆解为支持放置于 PPT 中的独立元素，包括但不限于：

- PNG 图片；
- 表格；
- 单独的文本；
- 文本框；
- 连线；
- 箭头；
- 矩形、圆形等基本矢量图形；
- 其他适合在 PowerPoint 中独立编辑的元素。

拆解完成后，应：

1. 将各元素分别作为可独立编辑对象处理；
2. 尽量保持原图中的位置、比例、对齐和层级关系；
3. 将这些元素重新放置到 PPT 页面中；
4. 生成最终 PPT 文件；
5. 如有需要，同时保留 SVG 或其他可继续编辑的矢量版本。

目标不是将整张 SVG 作为单张图片直接插入 PPT，而是尽可能还原为 **可编辑、可移动、可修改文本和样式的 PowerPoint 元素**。

## 3. 项目内部文档职责与冲突优先级

发生冲突时，遵循以下优先级：

1. **用户当前明确要求优先**；
2. 项目内部长期规则以 `AGENTS.md` 为准；
3. 动态状态以 `SCHEDULE.md` 为准；
4. 执行历史以 `WORKLOG.md` 的追加记录为准。

### AGENTS.md

`AGENTS.md` 只记录长期有效的：

- 研究规则；
- 证据规则；
- 建模规则；
- 实验规则；
- 成果核验规则。

不得将短期任务状态、当前阶段安排或临时执行记录写入 `AGENTS.md`。

### SCHEDULE.md

`SCHEDULE.md` 只记录：

- 当前阶段；
- 当前优先级；
- 任务状态；
- 阻塞项；
- 验收条件；
- 下一步计划。

动态任务状态应以 `SCHEDULE.md` 为准。

### WORKLOG.md

`WORKLOG.md` 只记录已经执行的操作。

默认规则：

- 禁止读取历史内容；
- 每次只能在文件末尾追加一条新的执行记录；
- 不修改既有历史记录；
- 不把未执行的计划写入 `WORKLOG.md`。

## 4. 学术文献检索与写作提示词示例

你是一名专业的学术文献检索与写作助手。请仅处理本提示词末尾提供的当前段落，为其中需要文献支持的观点检索并补充真实、可靠且高度相关的参考文献。

### 要求

1. 只处理当前段落，不扩展到其他章节，也不要生成 LaTeX、PDF、BibTeX 或项目文件。
2. 优先选择最近 5 年正式发表的同行评审期刊论文，必要时可引用少量经典文献。
3. 根据段落长度和论点数量匹配适量文献，通常为 5—10 篇，不得为了凑数量加入弱相关文献。
4. 文献应优先来自权威期刊、出版社官网、Crossref、Web of Science、Scopus、OpenAlex、ScienceDirect 等可靠来源。
5. 每篇文献必须核验题目、作者、年份、期刊和 DOI，禁止虚构、猜测或拼接文献信息。
6. 不能只根据论文题目判断相关性，应结合摘要、研究对象、方法和结论判断文献是否能够支持对应观点。
7. 在不改变原意的前提下，可以适度润色段落，使表达更加学术、严谨和连贯，但不得添加无文献依据的新结论。
8. 使用 APA 第 7 版作者—年份制插入文内引用，例如：

   - （Wang, 2023）
   - （Wang & Li, 2023）
   - （Wang et al., 2023）
   - （Chen et al., 2022; Wang et al., 2024）

9. 引用应紧跟其直接支持的句子，分布自然，不要每句话机械添加，也不要在同一位置堆积过多文献。
10. 无法找到可靠文献支持的观点，不要强行引用，可将其改为更谨慎的表达。
11. 文末按照 APA 第 7 版列出完整参考文献，并使用以下 DOI 格式：

    `https://doi.org/xxxxx`

12. 正文中的文献必须全部出现在参考文献表中，参考文献表中的文献也必须在正文中被引用。
13. 请直接给出最终结果，不要只提供检索建议或操作步骤。

### 输出格式

#### 一、补充引用并适度润色后的段落

#### 二、APA 第 7 版参考文献

#### 三、简要核验说明

列出每篇文献的 DOI 是否有效及主要核验来源。

### 以下为需要处理的当前段落

【将需要补充参考文献的段落粘贴在这里】

## 5. 长对话压缩与 JSON 摘要提示词

请将我们之间上述所有对话（包括您最初的提示）压缩成尽可能无损且保留关键信息和统计数据的形式。

目标是使后续语言模型能够：

- 完全恢复当前对话的主要上下文；
- 延续相同的概念框架；
- 恢复重要的用户偏好、约束和已完成工作；
- 保留关键数据、定义、文件、模型、实验条件及尚未解决的问题；
- 在新对话中继续工作时，尽量达到“对话从未中断”的效果。

最终结果应能够作为单一提示词重新导入语言模型。

请生成一个 **可重复使用的 JSON 代码摘要**。

要求：

1. 尽可能无损压缩，而不是只生成普通对话摘要；
2. 保留重要术语、变量、统计数据、文件名、路径、任务状态和规则；
3. 区分长期规则、当前状态、历史执行记录和用户偏好；
4. 对重复信息进行归并，但不要删除会影响后续判断的重要差异；
5. 明确记录已经确定的结论和尚未确定的问题；
6. 输出应方便后续 LLM 直接读取和继续执行。

## 6. 编码与工程执行准则

### 权衡说明

本准则优先保障严谨性，而非追求速度。

对于简单任务，可以酌情灵活处理；对于涉及多文件、模型重构、实验逻辑、数据处理、工程修改等任务，应严格遵循以下规则。

---

## 6.1 编码前先思考

不做无端假设，不回避疑问，主动披露权衡取舍。

编码实现前：

1. 明确说明你的假设；
2. 如有不确定之处，直接询问；
3. 若存在多种解读方式，全部列出，不要自行默认选择其中一种；
4. 若有更简洁的实现方案，主动说明；
5. 必要时可以提出不同意见；
6. 遇到不明确的内容应立即停止，说明困惑点并询问确认。

核心原则是：

> 澄清应发生在编码之前，而不是在实现错误之后。

---

## 6.2 优先保持简洁

使用最少的代码解决问题，不做任何推测性实现。

具体要求：

- 不实现需求之外的功能；
- 不对仅使用一次的代码做抽象封装；
- 不添加未被要求的“灵活性”或“可配置性”；
- 不为不可能出现的场景增加额外异常处理；
- 如果 200 行逻辑可以用 50 行实现，则应重写为更简单的方案。

执行前应自检：

> 资深工程师是否会认为当前设计过于复杂？

如果答案是肯定的，应继续简化。

---

## 6.3 精准改动

只修改必要内容，只清理由本次改动直接产生的冗余。

编辑已有代码时：

- 不“优化”相邻代码；
- 不修改无关注释；
- 不修改无关格式；
- 没有问题的代码不要重构；
- 遵循现有代码风格，即便存在个人偏好的其他写法；
- 如果发现无关的死代码，可以指出，但不要擅自删除。

当本次改动产生废弃内容时，可以清理：

- 因本次改动而不再使用的导入；
- 因本次改动而不再使用的变量；
- 因本次改动而不再使用的函数。

除非明确要求，否则：

- 不删除原本就存在的死代码；
- 不借机做大规模清理；
- 不进行无关重构。

检验标准：

> 每一行代码改动，都应能够直接对应到用户的具体需求。

---

## 6.4 目标驱动执行

先定义成功标准，再循环验证，直到满足要求。

应将任务转化为可验证目标。

示例：

- “新增校验”  
  → 为非法输入编写测试用例，再实现逻辑使测试通过。

- “修复 bug”  
  → 编写能够稳定复现问题的测试用例，再修复问题使测试通过。

- “重构 X 模块”  
  → 确保重构前后测试均能够正常通过。

对于多步骤任务，应先给出简要执行计划。

示例：

```text
1. 【执行步骤】 → 验证方式：【检查项】
2. 【执行步骤】 → 验证方式：【检查项】
3. 【执行步骤】 → 验证方式：【检查项】
```

清晰的成功标准能够支持独立推进迭代。

模糊的标准，例如：

> “先让它跑起来”

通常不足以支持可靠执行，需要进一步明确验收条件。

### 本准则生效的标志

- 代码差异中的无关改动明显减少；
- 因过度复杂导致的返工减少；
- 澄清类问题发生在编码之前，而不是错误发生之后；
- 每一项修改均有明确的验证方式；
- 实现过程围绕用户定义的目标，而不是围绕“顺手优化”展开。

## 7. 通用复杂任务启动提示词

适用于需要读取上下文、分析多个约束、修改文件或执行多步骤工作的任务。

```text
在开始执行前，先准确理解任务，不要立即修改。

请先完成以下检查：
1. 用简洁语言概括本次任务目标；
2. 列出必须满足的约束；
3. 列出明确不能修改或不能影响的内容；
4. 识别可能存在歧义的地方；
5. 给出最小可行执行方案；
6. 为每一步定义验收条件。

如果现有信息已经足够，则直接执行，不要为了形式反复询问。
如果存在会明显影响结果的关键歧义，再提出必要的问题。

执行原则：
- 优先最小改动；
- 不扩大任务范围；
- 不顺手重构；
- 不添加没有要求的功能；
- 每一步完成后按照验收条件检查；
- 最终明确说明实际完成了什么、未完成什么以及原因。
```

## 8. “禁止改动范围”提示词

```text
本次任务采用最小变更原则。

允许修改：
【填写允许修改的文件、模块、段落或功能】

明确禁止修改：
【填写不能修改的文件、接口、变量、实验参数、已有结论、排版等】

要求：
1. 不修改任务范围之外的内容；
2. 不做无关重构；
3. 不改变已有接口行为；
4. 不重新命名无关变量、函数或文件；
5. 不格式化整个文件；
6. 如果发现其他问题，只在最终说明中指出，不要顺手修复；
7. 每一处实际修改都必须能够直接对应到当前需求。
```

## 9. 代码审查提示词

```text
请对以下代码进行严格代码审查。

【Context：背景】
说明代码用途、所在系统和关键业务逻辑。

【Scope：审查范围】
仅检查：
- 正确性；
- 边界条件；
- 状态一致性；
- 异常处理；
- 数据流；
- 接口契约；
- 可能影响现有功能的回归问题。

【Concerns：重点担忧】
【填写当前最担心的问题】

【Constraints：约束】
- 不讨论纯风格问题；
- 不提出与当前功能无关的重构；
- 不因为“可能更优雅”而要求改写；
- 只有能够说明具体失败路径的问题才列为缺陷。

对每个问题按以下格式输出：
1. 严重程度：阻断 / 重要 / 一般
2. 位置：文件、函数或代码段
3. 问题：一句话说明
4. 触发条件
5. 后果
6. 原因
7. 最小修复建议
8. 是否需要测试验证

如果没有发现明确问题，应直接说明“未发现可确认的问题”，不要为了凑数量生成推测性问题。
```

## 10. Bug 复现与修复提示词

```text
请按照“先复现、后定位、再修复、最后回归验证”的顺序处理该 Bug。

现象：【填写错误现象】
预期行为：【填写预期行为】
实际行为：【填写实际行为】
相关文件：【填写文件】

第一步：复现
- 构造最小复现场景；
- 明确输入、环境和触发条件；
- 如果不能稳定复现，不要直接修改代码。

第二步：定位
- 沿真实调用链定位根因；
- 区分根因、表面症状和伴随问题；
- 不把猜测当作结论。

第三步：修复
- 只修复根因；
- 使用最小必要改动；
- 不借机重构周边代码。

第四步：验证
至少验证：
1. 原 Bug 已不能复现；
2. 正常输入仍然正常；
3. 相关边界条件未受到破坏；
4. 原有测试仍然通过。

最终输出：根因、修改位置、修改内容、验证方式、验证结果、剩余风险。
```

## 11. 变更影响面分析提示词

```text
在修改【目标对象】之前，请先分析它的影响范围。

请查找：
1. 定义位置；
2. 所有直接调用者；
3. 所有间接依赖；
4. 输入数据来源；
5. 输出数据消费者；
6. 相关配置；
7. 相关测试；
8. 相关文档；
9. 是否存在序列化、缓存、结果文件或历史数据依赖；
10. 修改后可能产生的兼容性问题。

输出：
一、目标对象当前职责
二、依赖关系：上游 → 当前对象 → 下游
三、潜在受影响位置
四、必须同步修改的位置
五、明确不需要修改的位置
六、推荐的最小修改方案

在完成影响面分析前，不要开始实际修改。
```

## 12. 多文件一致性检查提示词

```text
请检查以下多个文件之间是否保持一致：
```

## 27. 提示词版本管理规则

对于长期重复使用的提示词，建议同时记录：

```text
Prompt Name:
Version:
Purpose:
Applicable Tasks:
Required Inputs:
Forbidden Actions:
Output Schema:
Verification:
Last Updated:
Known Failure Modes:
```

推荐规则：
1. 实质逻辑变化时更新版本号；
2. 只修改措辞时更新修订号；
3. 不直接覆盖效果稳定的旧版本；
4. 记录导致失败的典型场景；
5. 将输入、约束、输出格式和验证方式分开；
6. 对长期工作流提示词建立固定验收项。

## 28. 推荐的通用提示词骨架

```text
【Task】
本次具体要完成什么。

【Context】
完成任务必须知道的背景。

【Scope】
允许处理的范围。

【Do Not Touch】
明确不能修改、不能推断、不能扩展的内容。

【Inputs】
提供哪些文件、数据、段落或代码。

【Constraints】
技术、学术、格式、时间或兼容性约束。

【Process】
要求采用怎样的分析或执行顺序。

【Verification】
如何判断任务已经正确完成。

【Output】
最终需要什么形式的结果。

【Failure Rule】
证据不足、信息缺失或无法确认时应如何处理。
```

一个提示词是否稳定，通常不取决于“角色描述有多长”，而更取决于：输入是否明确、范围是否明确、禁止项是否明确、输出结构是否明确、成功标准是否可验证，以及信息不足时是否规定了停止猜测的规则。
